# 复古拨盘电话 → PC → 语音控制游戏 · 设计文档

> 版本：v0.1（构思阶段）
> 日期：2026-11-20
> 状态：方案已定，未开始实现

---

## 一、项目目标

把一台**老式红色拨盘电话机**改造成电脑的输入设备：

```
拿起话筒 → 拨 "001" → 接通 → 说话 → AI 听懂 → 控制《钢铁雄心4》的兵力调度
```

### 做什么

- 拨盘保留机械结构，触点接到 MCU，解码出拨号数字
- 叉簧（挂机开关）作为"开始 / 结束"信号
- 话筒换成驻极体，听筒保留原动圈
- **整机对外只有一根 USB 线**（供电 + 音频 + 数据）
- PC 侧：语音转文字 → 大模型解析成命令 → 作用到游戏

### 不做什么

| 不做 | 原因 |
|---|---|
| 自定义 ASIC 流片 | 成本几十万起，本项目只需画 PCB |
| 90V AC 打铃 | 不安全，且不是核心体验；需要时用小喇叭播铃声 |
| 4 位/8 位电话键盘（DTMF）| 拨盘是**脉冲**式，不是双音多频 |
| 替换机械拨盘为光电/霍尔 | **手感与咔哒声是本项目的灵魂** |
| 实时（不暂停）语音指挥 | HOI4 可随时暂停，语音本来就不该抢实时 |

## 二、系统架构

```
┌──────────────────── 老电话外壳 ────────────────────┐
│                                                    │
│  拨盘（脉冲触点）──► MCU GPIO + EXTI               │
│  叉簧（挂机触点）──► MCU GPIO                      │
│                                                    │
│  话筒（驻极体）──► MAX9814 ──► USB 声卡 MIC IN     │
│  听筒（动圈）  ◄──────────────  USB 声卡 LINE OUT  │
│                                                    │
│  ┌─────────── 内部 ───────────┐                    │
│  │  USB Hub ─┬─ USB 声卡      │                    │
│  │           └─ MCU（小开发板）│                    │
│  └────────────────────────────┘                    │
└────────────────────┬───────────────────────────────┘
                     │ 一根 USB-C（从原电话线孔引出）
                     ▼
                ┌─────────┐
                │   PC    │
                └────┬────┘
                     │
        ┌────────────┼─────────────┐
        ▼            ▼             ▼
    串口事件     声卡音频      控制管线
   ("001")    (16k PCM)    Whisper → LLM → 执行
```

### 关键设计决定

| 决定 | 理由 |
|---|---|
| **音频与拨号走两条独立通路** | 任一路出问题都不影响另一路，便于单独调试 |
| **音频用成品 USB 声卡，不用 MCU 做** | 省掉 I2S/DMA/UAC 的全部调试成本，音质更好 |
| **MCU 只做拨盘解码 + 串口** | 职责单一，几十行代码即可 |
| **内部用小 USB Hub 合成一根出线** | 外部只看到 1 根线，但内部全是标准器件、标准驱动 |

## 三、硬件方案

### 3.1 器件清单

| 类别 | 器件 | 规格 | 数量 | 参考价 |
|---|---|---|---|---|
| 主体 | 老式拨盘电话机 | 二手，外壳完好 | 1 | 30~80 |
| MCU | ESP32-S3-Zero 或同类小开发板 | **18×18 mm**，带 USB CDC | 1 | 20 |
| 音频 | USB 声卡 | Type-C 小方块，带 MIC IN + 耳机口 | 1 | 15 |
| 音频 | MAX9814 模块 | 带 AGC 的麦克风前置放大 | 1 | 5 |
| 音频 | 驻极体咪头 | 全指向 | 1 | 1 |
| 音频 | PAM8403 功放 | **可选**，听筒声音不够时加 | 1 | 3 |
| 互联 | USB Hub 模块 | 4 口，尽量选小板 | 1 | 10 |
| 互联 | USB-C 母座 + 线材 | 从原电话线孔引出 | 1 | 5 |
| 被动 | 电阻/电容/杜邦线/热熔胶 | RC 滤波、固定 | — | 15 |
| | **合计** | | | **约 100 元** |

### 3.2 尺寸核算

老式拨盘电话内部空间：**约 80 × 120 × 40 mm**，拨盘后方另有约 ⌀60 mm 空腔。

| 组件 | 占用 |
|---|---|
| USB Hub 模块 | 30 × 20 mm |
| USB 声卡 | 25 × 20 mm |
| MCU 板 | 18 × 18 mm |
| MAX9814 | 15 × 10 mm |
| **合计 ≈** | **50 × 35 mm** |

**空间充足**，还有大量余量放电源滤波和走线。

### 3.3 拨盘接线

拨盘下方通常有 2~3 组触点：

| 触点 | 作用 | 是否使用 |
|---|---|---|
| **脉冲触点（pulse）** | 拨号时反复通断，**数量 = 拨的数字** | ✅ **用这个** |
| 短路触点（shunt） | 拨号时短路话筒，防咔哒声进线路 | ❌ 忽略 |
| 通话/挂机触点 | 与叉簧配合 | 视情况 |

```
脉冲触点 ──┬── GND
           └── GPIO（输入 + 内部上拉）
               └─ 并联 100 nF 到 GND（RC 滤波，压触点抖动）

叉簧触点 ──┬── GND
           └── GPIO（输入 + 内部上拉）
```

> ⚠️ 拨号触点一端接 GND，另一端接 GPIO 并开内部上拉，是最省事且抗干扰的接法。
> 若要彻底隔离电话机的机械噪声，可加 PC817 光耦。

### 3.4 供电核算

USB 2.0 端口：**5V / 500 mA**

| 器件 | 典型电流 |
|---|---|
| MCU（WiFi 关闭）| 50 mA |
| USB 声卡 | 20 mA |
| MAX9814 + 驻极体 | 3 mA |
| USB Hub 自身 | 15 mA |
| PAM8403（小音量）| 50 mA |
| **合计** | **≈ 140 mA** ✅ |

> 余量充足。若开启 WiFi，峰值可达 350 mA，总电流约 440 mA，接近上限 ——
> **本项目不需要 WiFi，建议关闭。**

## 四、拨盘解码（本项目唯一必须从零实现的部分）

### 4.1 脉冲式拨号原理

老式拨盘**不是**双音多频（DTMF），而是**脉冲**拨号：

```
拨 "1"  →  1 个脉冲
拨 "5"  →  5 个脉冲
拨 "9"  →  9 个脉冲
拨 "0"  → 10 个脉冲      ★ 反直觉：0 是脉冲最多的
```

**数字 = 数脉冲个数。**

时序（老式标准约 10 脉冲/秒）：

```
脉冲周期   ≈ 100 ms
脉冲宽度   ≈ 40~60 ms（断/通各占一部分）
位间隔     ≈ 200 ms 以上（两个数字之间）
```

所以拨 "001" 的波形是：

```
10 个脉冲 ──停── 10 个脉冲 ──停── 1 个脉冲
  ↑ 数字 0         ↑ 数字 0        ↑ 数字 1
```

### 4.2 状态机

```
        ┌──────────────────────────────────────┐
        │                                      │
        ▼                                      │
   ┌─────────┐  下降沿    ┌──────────┐        │
   │  IDLE   │──────────►│ COUNTING │        │
   └─────────┘           └────┬─────┘        │
        ▲                     │ 下降沿: n++   │
        │                     │               │
        │  输出一位           │ 200ms 无脉冲  │
        └─────────────────────┘               │
                                              │
   拼出数字串 → 1.5 s 无新数字 → 触发"拨号完成"
```

**这个模式与 GPS 组行器完全相同** —— 都是"用超时切分数据单元"：

| 场景 | 数据单元 | 切分依据 |
|---|---|---|
| GPS 组行 | 一条 NMEA 语句 | 200 ms 无字节 |
| 拨盘解码 | 一位数字 | 200 ms 无脉冲 |

### 4.3 实现要点

| 要点 | 说明 |
|---|---|
| 用 **EXTI 下降沿**计数 | 中断里只做 `n++`，其余全部放主循环 |
| 用 **定时器**做超时判定 | 记录"最后一次脉冲时刻"，主循环比较差值 |
| **只在正向转动时计数** | 拨到底松手会回弹，回弹也可能产生触点通断 |
| 软件去抖 | RC 之后仍需 20~50 ms 的软件确认 |
| `n == 0` 时输出 `0` | `0` 是 10 个脉冲，但某些接法会得到 0，需实测确认 |

### 4.4 必须先实测的三件事（用万用表，半小时）

1. **拨 1 时脉冲触点响几次？** —— 确认哪组是脉冲触点
2. **拨 0 时响几次？** —— 确认是 10 次
3. **叉簧摘机/挂机各是什么状态？** —— 确认常闭还是常开

> **不测这三件事就开始写代码，几乎必定要返工。**

## 五、软件架构

### 5.1 MCU 侧（几十行）

```
初始化 GPIO + EXTI + TIM
主循环：
    读脉冲计数 → 超时切位 → 拼字符串
    读叉簧状态 → 摘机/挂机
    通过 USB CDC（虚拟串口）发送事件：
        "HOOK 1"      摘机
        "HOOK 0"      挂机
        "DIGIT 0"     拨了一位 0
        "DIAL 001"    拨号完成
```

### 5.2 PC 侧管线

```
┌─────────────┐   ┌──────────┐   ┌─────────┐   ┌──────────┐
│ 串口监听     │──►│ 拨号状态 │──►│ 录音    │──►│ Whisper  │
│ (pyserial)  │   │ "001" ？ │   │ (声卡)  │   │ 语音→文字│
└─────────────┘   └──────────┘   └─────────┘   └────┬─────┘
                                                    ▼
┌─────────────┐   ┌──────────┐   ┌──────────────────┐
│ 游戏执行     │◄──│ 命令解析 │◄──│ LLM（自然语言→   │
│ (见第七节)   │   │ 校验/纠错│   │      结构化命令）│
└─────────────┘   └──────────┘   └──────────────────┘
```

### 5.3 技术选型

| 环节 | 方案 | 说明 |
|---|---|---|
| 串口 | `pyserial` | 读 COM 口事件 |
| 录音 | `sounddevice` / `pyaudio` | 从 USB 声卡录 16 kHz 单声道 |
| **语音识别** | **faster-whisper**（本地） | CPU 可跑 small 模型，短句足够；需要更快可上云端 |
| 命令解析 | 本地 LLM 或云端 API | 输出结构化 JSON，如 `{"action":"move","unit":"3rd Army","target":"Warsaw"}` |
| 状态机 | 自写 | `IDLE → DIALING → CONNECTED → LISTENING → DONE` |

### 5.4 语音交互流程

```
1. 摘机（叉簧）           → 播放"嘟——"提示音
2. 拨 001                → PC 收到 "DIAL 001"
3. 校验号码              → 正确则播放"已接通"合成语音
4. 录音，VAD 检测说话结束  → 送 Whisper
5. 文字显示在屏幕          → 送 LLM 解析成命令
6. 执行 + 语音反馈         → "第三集团军已向华沙移动"
7. 挂机                   → 结束，回到 IDLE
```

## 六、拨号规则设计

| 号码 | 含义 |
|---|---|
| `001` | 接通 AI |
| `000` | 挂断 / 重听 |
| `002` | 切换游戏场景（预留）|
| 其他 | 播放"号码不存在"提示音 |

> 「拨 001 接通」这个设定本身就是复古仪式感的一部分，值得保留。

## 七、游戏控制（**风险最高的一段**）

### 7.1 核心约束

**《钢铁雄心4》没有任何官方外部控制 API。**

没有 socket、没有 REST、没有可被外部读写的运行时文件。

### 7.2 三种方案对比

| 方案 | 做法 | 可靠性 | 工作量 |
|---|---|---|---|
| **A 键鼠模拟** | 屏幕识别 + `pyautogui` 点按 | 中（UI 变化即失效）| 中 |
| **B 控制台命令** | `~` 打开控制台输入命令 | 低（精细操作无对应命令）| 低 |
| **C Mod + 快捷键** | 写 mod 加决策，每个决策绑快捷键 | **较高** | 高 |

### 7.3 推荐：C 为主，A 为辅

```
语音 → LLM → {"action":"move_army","army":3,"target":"warsaw"}
                    ↓
            映射到预先定义的"决策/快捷键"
                    ↓
            pyautogui 发送按键
```

**用 mod 把"命令集"预先定义好**，语音只负责选择其中一个 —— 这样：
- 不需要屏幕识别定位省份（最大的不确定性被消除）
- 命令集虽然有限，但兵カ调度实际操作就那么几种

### 7.4 诚实标注

> 这一段**尚未验证可行性**。
> 控制台具体有哪些命令、mod 决策能否绑定快捷键，
> 需要实际打开游戏逐项确认，不能凭印象设计。

## 九、风险与坑清单

| # | 坑 | 影响 | 对策 |
|---|---|---|---|
| 1 | **"0" 是 10 个脉冲** | 解码全错 | 实测确认 |
| 2 | 回弹产生多余脉冲 | 数字多算 | 只在正向转动时计数 + 位间超时 |
| 3 | 碳粒话筒要直流偏置 | 无声音 / 噪声大 | **直接换驻极体** |
| 4 | 触点抖动 | 数字乱跳 | RC 滤波 + 软件去抖 |
| 5 | 游戏侧无 API | 项目卡在最后一段 | 用 mod + 快捷键收敛命令集 |
| 6 | Whisper 延迟 | 交互不够"即时" | 本地 small 模型，或云端 API |
| 7 | USB 电流接近上限 | 掉电重启 | 关闭 WiFi，控制音量 |
| 8 | 内部走线杂乱 | 装不回去 | 热熔胶固定 + 扎带 |
