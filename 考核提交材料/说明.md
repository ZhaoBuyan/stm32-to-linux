# 简要说明

> 配套工程：`STM32F429/DHT11_Test`

## 一、工程概述

基于野火 STM32F429 开发板的裸机灯控与温湿度监测终端。

- **按键**：KEY1 开灯、KEY2 关灯（10 ms 周期扫描 + 20 ms 消抖，按住不重复触发）
- **串口**：`@` 开头、`\n` 结束的命令协议，控制 / 查询同一个 LED
- **温湿度**：DHT11 每 2 秒采样一次，`@ENV?` 返回最近一次有效数据
- **接收超时**：TIM6 产生 10 ms 时基，从收到 `@` 起 2 秒内没有 `\n` 则返回一次 `ERR,TIMEOUT`

## 三、操作方法

**串口参数**：115200 / 8 位数据位 / 无校验 / 1 位停止位。用串口调试助手的「文本发送 + 追加换行」。

| 功能 | 发送 | 响应 |
| --- | --- | --- |
| 开灯 | `@LED=1` | `OK,LED=1` |
| 关灯 | `@LED=0` | `OK,LED=0` |
| 灯状态查询 | `@LED?` | `LED=1` |
| 环境查询 | `@ENV?` | `ENV,T=26,H=58` |
| 启动闪烁 | `@BLINK=1` | `OK,BLINK=1` |
| 停止闪烁（并关灯） | `@BLINK=0` | `OK,BLINK=0` |
| 开启周期上报 | `@REPORT=1` | `OK,REPORT=1` |
| 关闭周期上报 | `@REPORT=0` | `OK,REPORT=0` |
| 非法命令 | `@LED=3` / `@LED=1ABC` | `ERR,CMD`（LED 不变） |
| 超长命令 | 超过 32 字节 | `ERR,LENGTH` |
| 不完整命令 | 只发 `@LED=` 不加换行，等 2 秒 | `ERR,TIMEOUT` |
| 无有效数据 | `@ENV?` | `ERR,SENSOR` |

**按键**：KEY1 开灯、KEY2 关灯。按键操作会退出闪烁模式。

## 四、关键设计

### 1. 三个时间源分工

| 时间源 | 精度 | 用途 |
| --- | --- | --- |
| TIM6 中断累加的 `g_tick10` | 10 ms | 按键扫描、接收超时、闪烁、上报周期、DHT11 采样调度 |
| SysTick（`HAL_GetTick`） | 1 ms | HAL 内部延时 |
| DWT 周期计数器 | 1 µs | DHT11 单总线时序 |

微秒级时序不能用 `HAL_Delay`（最小 1 ms），所以 DHT11 驱动用 DWT 数 CPU 周期。

### 2. 定时器中断只计数

```c
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim) {
    if (htim->Instance == TIM6) {
        g_tick10++;          /* 只做这一件事 */
    }
}
```

命令解析、串口响应、读传感器全部在主循环完成。

### 3. 串口「逐字节中断 + 接收状态机」

不用 DMA + 空闲中断，而用 `HAL_UART_Receive_IT` **每次收 1 字节**，在中断里喂给接收状态机。原因：本协议要求「从收到 `@` 起 2 秒内没收到 `\n` 就算超时」，必须**逐个字节地知道谁在什么时候到达**；空闲中断只能在一帧结束后才把整块数据交出来。

```
【IDLE】
   └─ '@'  → 清空缓冲、记录起始时刻 → 【RECVING】
【RECVING】
   ├─ '\n'  → 置"整行就绪"标志 → 主循环解析 → 回 IDLE
   ├─ '\r'  → 忽略
   ├─ '@'  → 丢弃旧命令，以新 '@' 重新开始
   ├─ 其他  → 存缓冲；超过 31 字符则置超长标志
   └─ 满 2 秒 → 主循环发一次 ERR,TIMEOUT → 回 IDLE
```

### 4. LED 状态的唯一来源

`LED_GetState()` 不像素变量，而是**直接读 `ODR` 寄存器的 bit10**（共阳极：位为 0 = 灯亮）。这样闪烁过程中查询也一定返回当时真实状态，不存在「记的状态和实际不一致」。

### 5. 中断与主循环的分工

- **中断里**：TIM6 只 `g_tick10++`；UART 只 `Cmd_FeedByte(字节)`（收字节、改状态机）——快进快出
- **主循环里**：解析命令、发响应、读 DHT11
- **中断使能**：USART1 与 TIM6 都在 CubeMX 的 NVIC 中使能了全局中断。这一点必须做——`HAL_UART_Receive_IT()` 只打开了外设内部中断，如果 NVIC 里没使能，CPU 永远收不到中断，表现为「发什么都不回」且不报错

响应（串口发送）全部放在主循环，中断里绝不发串口。

## 五、测试结论与已知可改进点

**必做 6 项、提高 4 项功能，已在真机上逐项实测通过**（明细见《引脚表与测试记录》）。

以下两条是本实现**已知的可改进点**，不影响验收功能，如实列出：

| # | 现状 | 更好的做法 |
| --- | --- | --- |
| 1 | 超时 / 闪烁 / 上报用「`Cmd_Tick10ms()` 被调用的次数」计时 | 收到 `@` 时记录当刻的 `g_tick10`，之后用 `g_tick10 - start >= 200` 判断。无符号相减自动回绕，tick 溢出也正确；且不会因 DHT11 读取阻塞（约 20 ms）丢掉几个 tick 而产生约 1% 误差 |
| 2 | 串口接收缓冲区由中断和主循环共用 | 极端情况（10 ms 内连发两条命令，或主循环正好卡在 DHT11 读取中）可能丢掉一条响应。更稳妥的做法：中断只把字节塞进环形缓冲，接收状态机整体搬到主循环 |

**关于不使用 DMA 的说明**：本协议要求「计时从 `@` 开始、后续字符不重新计时、接收中再遇 `@` 要重新开始」，这些规则全都作用在**接收过程中**，必须逐字节知道每个字节何时到达。DMA + 空闲中断只能在一帧结束后交出整块数据，无法满足，因此**有意**采用逐字节中断接收。
