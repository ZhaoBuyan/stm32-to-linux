# 事件字典

> T01 交付物之二。事件 = 一瞬间发生、会促使状态机做判断的信号。
> 判断一次状态转移是否合法，先看事件，再看守卫条件。

## 一、事件从哪来（分类标准）

判断标准只有一句话：

> **是谁调用 `DeviceFsm_Dispatch()` 把这个事件发给状态机的？**

| 来源 | 判断 | 举例 |
| --- | --- | --- |
| **外部事件** | 由用户操作或上位机命令触发 | 按键、旋钮、串口命令 |
| **内部事件** | 由系统自身代码检测后抛出 | 初始化完成、驱动报错、超时判定 |

外部事件进不了状态机自己 —— 必须经过一次"翻译"：
按键扫描、串口帧解析这些**前端模块**把原始输入翻译成事件，再交给状态机。
**状态机不认识按键，只认识事件。**

## 二、事件词典（8 个）

| 事件 | 来源 | 产生的模块 | 含义 | 携带信息 |
| --- | --- | --- | --- | --- |
| `EVT_BOOT_OK` | 内部 | 初始化流程 | 关键外设自检完成，可以进入待命 | 无 |
| `EVT_PREPARE` | 外部 | 按键 / 串口 | 请求进入准备状态（上料、设参数、自检） | 无 |
| `EVT_START` | 外部 | 按键 / 串口 | 请求启动执行 | 无 |
| `EVT_PAUSE` | 外部 | 按键 / 串口 | 请求暂停，保留现场 | 无 |
| `EVT_RESUME` | 外部 | 按键 / 串口 | 请求从暂停继续执行 | 无 |
| `EVT_STOP` | 外部 | 按键 / 串口 | 请求停止，回到空闲（放弃现场） | 无 |
| `EVT_FAULT` | 内部 | 各驱动 / 超时判定 | 检测到故障，要求安全停机 | 故障码（示例实现中为布尔故障标志） |
| `EVT_RESET` | 外部 | 按键 / 串口 | 故障已排除，请求复位回空闲 | 无 |

## 三、几处需要说明的地方

### 3.1 为什么 `FAULT` 算内部事件

用户不会去"按一个故障键"。是驱动代码自己发现"MPU6050 读不到"、
"DHT11 校验失败"、"存储写不进"，然后主动把这个事件抛给状态机。

所以判定依据不是"这件事是不是外部引起的"，而是"**谁在代码里发出了这个事件**"。

### 3.2 超时不是新事件

8 个事件里没有"超时"。超时的处理方式是：

```
进入 RUNNING 时记录 entered_at_ms
主循环每帧调用 DeviceFsm_Tick(now_ms)
    若 now_ms - entered_at_ms >= run_limit_ms
        则内部产生 EVT_FAULT
```

也就是说，**超时只是产生 `EVT_FAULT` 的一种原因**，不需要单独的转移路径。
这样"任何原因导致的异常"都汇聚到同一条 `FAULT → ERROR` 上，异常出口只有一个，不容易漏。

### 3.3 暂停期间不计时

示例定义的是"**连续运行超时**"：每次重新进入 RUNNING 都重置计时起点，
暂停期间不累计运行时间。

这是任务书允许的两种定义之一（另一种是"累计运行时间，暂停不计但恢复不重置"）。
本设计采用**前者**，理由是它和 `entered_at_ms` 一个字段就能实现，代码更简单、行为更可预测。
若要改成累计计时，需要额外一个 `accumulated_ms` 字段，并在 PAUSE 时结算。

### 3.4 重复的 `FAULT` 不重复通知

ERROR 状态下再次收到 `EVT_FAULT`，示例实现返回 `FSM_OK` 但**不重复触发迁移回调**。
这样上层不会因为"故障持续存在"而被反复通知，避免重复打印日志或反复执行停机动作。

### 3.5 没有携带数据的事件

本设计 8 个事件都不带负载（payload），只用一个枚举值表示。
任务书场景（T07 综合项目）如果需要"指定预热温度"之类的参数，
应该扩展为 `事件 + 参数结构体`，而不是给枚举加几十个成员。
