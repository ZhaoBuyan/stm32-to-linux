# 验收推演记录

> T01 交付物之四。
> 每个用例按"**初始状态 → 输入事件 → 守卫判断 → 结果 → 终态 → 不变量检查**"逐条推演，
> 结论必须能对着《转换表》找到对应行号。

推演约定：
- 下表"表#"指《转换表.md》里的行号；"忽略"指第二张表（未列出的组合）。
- 每次推演都假设设备刚上电，除用例明确说明外没有额外故障。
- 推演是**纸面推演**（T01 不写代码），不是运行结果。

## M01：`IDLE` 收到 `START`，不能跳过 `READY`

| 步骤 | 内容 |
|---|---|
| 初始状态 | `IDLE`（已通过自检并 `BOOT_OK`，尚未执行 `PREPARE`）|
| 输入事件 | `EVT_START` |
| 查表 | 《转换表》**第二张表**：`IDLE + START` → 忽略。`START` 只在 `READY` 是合法的（表 #4）|
| 守卫判断 | 不进入守卫判断 —— 该状态下这个事件**根本不接受** |
| 结果 | 返回 `FSM_IGNORED`，**不迁移**，不调用迁移回调 |
| 终态 | `IDLE` |
| 不变量检查 | `IDLE` 要求"执行机构断电、无料未备" → 保持成立 ✅ |
| 为什么必须这样 | `PREPARE` 里有真实动作（上料、设参数、预热）。允许 `IDLE + START` 就等于**悄悄跳过准备**，设备可能带着未加载的参数运行 |
| 预期 vs 实际 | 预期保持 `IDLE`；纸面推演结果一致 |

**反例说明**：如果允许 `IDLE → RUNNING`，那么"准备"这一步就永远可以不执行，
`READY` 状态也就没有存在的意义了。

## M02：`RUNNING` 收到 `PAUSE`，进入 `PAUSED`

| 步骤 | 内容 |
|---|---|
| 初始状态 | `RUNNING`（`entered_at_ms` 已记录，执行机构通电推进中）|
| 输入事件 | `EVT_PAUSE` |
| 查表 | 表 **#6**：`RUNNING --[PAUSE]--> PAUSED`，无守卫 |
| 守卫判断 | 无，直接通过 |
| 动作 | ① 停止推进（但**保持通电**）；② 结算本段运行时间 |
| 结果 | 返回 `FSM_OK`，触发迁移回调 `(RUNNING → PAUSED, EVT_PAUSE)` |
| 终态 | `PAUSED` |
| 不变量检查 | `PAUSED` 要求"保持通电但不推进、计时暂停" → 动作①保证不推进，动作②保证计时暂停 ✅ |
| 边界确认 | 暂停期间 `DeviceFsm_Tick()` **不再判定运行超时**（超时只在 `RUNNING` 检查），所以暂停可以持续任意久 |
| 预期 vs 实际 | 预期 `PAUSED`；推演一致 |

## M03：`ERROR` 收到 `RESET`，但故障仍存在 → 保持 `ERROR`

| 步骤 | 内容 |
|---|---|
| 初始状态 | `ERROR`（此前某状态收到 `FAULT`，`fault_active == true`，执行机构已断电）|
| 输入事件 | `EVT_RESET` |
| 查表 | 表 **#14**：`ERROR --[RESET 且 fault_active == true]--> ERROR（保持）` |
| 守卫判断 | 守卫条件是 `fault_active == false`；当前 `fault_active == true` → **不满足** |
| 动作 | 无（不迁移，不清故障）|
| 结果 | 返回 `FSM_GUARD_REJECTED`（**注意不是 `FSM_IGNORED`**）|
| 终态 | `ERROR` |
| 不变量检查 | `ERROR` 要求"执行机构必须断电；故障未清时 `RESET` 被拒绝" → 两条都成立 ✅ |

**为什么必须区分两种返回值**

- `FSM_IGNORED`：这个状态里**没有**这个事件（例：`IDLE + RESET`）
- `FSM_GUARD_REJECTED`：这个事件**在这里是合法的**，只是**现在还不能**（本例）

调用方看到 `GUARD_REJECTED` 应该提示"请先排除故障"，而不是"这个操作不支持"。
两者混用会让现场排查的人找错方向。

**正确的复位流程**（两步，顺序不能反）

```
1. 故障已排除 → DeviceFsm_SetFault(f, false, now)   // 清标志，仍留在 ERROR
2. 发 EVT_RESET                                     // 此时守卫通过 → IDLE
```

如果只发 `RESET` 而不清标志，会**一直卡在 ERROR** —— 这是**故意的设计**，
防止"故障还在就按复位"把报警灯关掉而火还在烧。

## M04：`PAUSED` 收到 `STOP`，回到 `IDLE`

| 步骤 | 内容 |
|---|---|
| 初始状态 | `PAUSED`（执行机构保持通电但不推进）|
| 输入事件 | `EVT_STOP` |
| 查表 | 表 **#11**：`PAUSED --[STOP]--> IDLE`，无守卫 |
| 守卫判断 | 无，直接通过 |
| 动作 | 执行机构**断电**，放弃本次任务现场 |
| 结果 | 返回 `FSM_OK`，触发迁移回调 |
| 终态 | `IDLE` |
| 不变量检查 | `IDLE` 要求"执行机构断电" → 动作里断电 ✅ |
| 对比 `RESUME` | `RESUME`（表 #10）会回到 `RUNNING` 并**保留现场**；`STOP` 回 `IDLE` 并**丢弃现场**。这就是"暂停"和"停止"的本质区别 |
| 预期 vs 实际 | 预期 `IDLE`；推演一致 |

## 附加推演：暂停恢复后计时必须重置（对应表 #10）

这条不在 M01~M04 里，但它证明了"连续运行计时"的定义，值得单独推一遍。

| 步骤 | 内容 |
|---|---|
| ① | `READY --START--> RUNNING`，记 `entered_at_ms = 1000`，`run_limit_ms = 5000` |
| ② | 运行到 `t = 4000`，已持续 `3000 ms`，**未超时** |
| ③ | 收到 `PAUSE` → `PAUSED`，结算本段 `3000 ms` |
| ④ | 暂停到 `t = 20000`（暂停 `16000 ms`）|
| ⑤ | 收到 `RESUME` → `RUNNING`，**重置 `entered_at_ms = 20000`** |
| ⑥ | 运行到 `t = 24000`，本次已持续 `4000 ms` → **仍未超时** |
| ⑥' | 如果是"累计计时"：`3000 + 4000 = 7000 ms > 5000` → **应该已经超时** |

**结论**：本设计采用**连续运行计时**（表 #10 的动作"重置 `entered_at_ms`"），
不是累计计时。这个定义必须和《事件字典》§3.3 保持一致。

> 任务书允许两种定义，但**必须写明是哪一种**。本设计选连续计时，理由是
> `entered_at_ms` 一个字段就能实现，代码更简单、行为更可预测。
> 若改成累计计时，需要额外 `accumulated_ms` 字段，并在 `PAUSE` 时结算。
