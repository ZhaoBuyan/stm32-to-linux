## 三、三种故障与恢复场景

三种场景覆盖了三类不同性质的故障：**自检失败**（启动期）、**运行期硬件故障**（外部原因）、
**运行超时**（系统自身判定）。它们的共同点是**都汇聚到同一个 `ERROR` 状态**，
恢复路径也都是同一条 `ERROR --[RESET 且故障已清]--> IDLE`。

### 场景 1：上电自检失败（启动期故障）

| 项目 | 内容 |
|---|---|
| 现象 | 上电后关键外设（如执行机构驱动、传感器总线）自检不通过 |
| 路径 | `INIT --[FAULT]--> ERROR` |
| 此时状态 | `ERROR`，执行机构断电 |
| 判定依据 | 自检代码给出具体的失败项（故障码）|
| 恢复动作 | ① 现场排查 → ② 修复后**重新上电**，或 ③ 调用 `DeviceFsm_SetFault(f, false, now)` 清标志后发 `EVT_RESET` |
| 恢复后 | `IDLE`，需要重新走 `PREPARE` |
| 为什么这样设计 | 自检没过就绝不能进 `IDLE`。让用户"重试"比让设备"带病运行"安全 |

**不允许的路径**：`INIT --[BOOT_OK]--> RUNNING`（跳过 `IDLE`/`READY`）。
自检完成 ≠ 准备好，更 ≠ 可以启动。

---

### 场景 2：运行中硬件故障（外部原因）

| 项目 | 内容 |
|---|---|
| 现象 | `RUNNING` 或 `PAUSED` 期间，驱动报告设备断线（例：执行机构反馈丢失、传感器无响应）|
| 路径 | `RUNNING --[FAULT]--> ERROR` 或 `PAUSED --[FAULT]--> ERROR`（表 #8 / #12）|
| 此时状态 | `ERROR`，执行机构**立即断电** |
| 关键动作 | 断电必须是**进入 ERROR 的第一动作**。留着能量等救援是危险的（堵转发热、继电器卡死）|
| 故障持续时 | 上游会反复报 `FAULT`。`ERROR + FAULT` 返回 `FSM_OK` 但**不重复触发迁移回调**（表 #15），避免反复执行停机动作和刷日志 |
| 恢复动作 | ① 排除硬件故障 → ② `DeviceFsm_SetFault(f, false, now)` → ③ 发 `EVT_RESET` → ④ `IDLE` |
| 恢复后 | `IDLE`，本次任务现场已丢弃，需重新 `PREPARE` |
| 为什么这样设计 | 运行中出故障，**先停再查**。不允许"自动重试继续跑"，因为重试可能造成二次损坏 |

**特别注意**：从 `PAUSED` 进 `ERROR` 时，`PAUSED` 的不变量是"保持通电但不推进"，
而 `ERROR` 要求"必须断电"——所以这条转移的**动作里必须显式断电**，
不能因为"暂停时已经不动了"就省略。

---

### 场景 3：运行超时（系统自身判定的故障）

| 项目 | 内容 |
|---|---|
| 现象 | `RUNNING` 持续运行时间超过 `run_limit_ms`，仍未收到 `PAUSE`/`STOP` |
| 判定 | 主循环每帧调 `DeviceFsm_Tick(now_ms)`，内部判断 `now_ms - entered_at_ms >= run_limit_ms` |
| 路径 | 判定成立时**内部产生 `EVT_FAULT`** → `RUNNING --[FAULT]--> ERROR`（表 #9）|
| 此时状态 | `ERROR`，执行机构断电，记录"运行超时"故障码 |
| 恢复动作 | 同场景 2：清标志 → `EVT_RESET` → `IDLE` |
| 为什么这样设计 | 超时是"没人管"的信号。可能是操作员走了、也可能是控制逻辑卡住。**先停**比继续跑安全 |
| 为什么不做成独立事件 | 如果给超时单独加一个事件和一条边，异常出口就变成两个。让它复用 `FAULT` 通道，**异常出口只有一个**，不会漏 |

**超时定义（必须写明）**：本设计采用**连续运行计时** ——
每次重新进入 `RUNNING` 都重置 `entered_at_ms`，暂停期间不累计。
（另一种"累计运行时间"的定义需要额外 `accumulated_ms` 字段，本设计不采用。）

---

### 三种场景的共同点（这就是设计意图）

```
场景 1 自检失败  ─┐
场景 2 运行期故障 ├──▶  ERROR（断电 + 锁存故障）  ──RESET 且故障已清──▶  IDLE
场景 3 运行超时  ─┘
```

| 共同规则 | 理由 |
|---|---|
| **出口只有一个**：`ERROR → IDLE` | 异常路径少，越不容易漏 |
| **入口有很多，但都断电** | 不管什么原因进 ERROR，第一动作都是安全停机 |
| **不存在 `ERROR → RUNNING`** | 任务书明确禁止。故障没清就恢复运行 = 带着故障跑 |
| **`RESET` 必须过守卫** | `fault_active == false` 才放行。这是"先排除再复位"的强制检查 |
| **恢复后一律回 `IDLE`** | 现场已丢弃，必须重新 `PREPARE`。不允许"恢复到半路" |

## 六、这四份文件之间的关系

```
状态词典.md ──┐
              ├──▶ 转换表.md ──▶ 状态图.png ──▶ 验收推演记录.md
事件字典.md ──┘        │                              │
                       └────────────── 互相校验 ──────┘
```

- `状态词典` 定义"有哪些房间"，`事件字典` 定义"有哪些敲门方式"
- `转换表` 是两者的**笛卡尔积**里挑出合法的那些
- `状态图` 是 `转换表` 的图形表达（内容必须一致）
- `验收推演` 用具体输入去验证 `转换表` 的结论

**一致性要求**：改了其中任何一份，其余三份都要跟着改。这是 T01 最重要的工程习惯。
