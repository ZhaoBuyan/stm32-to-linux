## 一、先把全貌记住

### 三个模块、三条线

```
                    ┌─────────────────────────────────────┐
   按键 KEY1/KEY2 ──▶│ main.c 主循环（每 10ms 一轮）        │
                    │   ① Key_Scan()  → LED_On/Off        │
   串口 ──中断──▶   │   ② Cmd_Tick10ms()                  │
                    └─────────────────────────────────────┘
                                    │
                    ┌───────────────┴───────────────┐
                    ▼                               ▼
              cmd.c 命令层                     dht11.c 传感器
        （收字节/解析/超时/闪烁/上报）      （每 2 秒读一次）
```

### 三个时间源，别搞混

| 时间源 | 精度 | 用在哪 |
| --- | --- | --- |
| `g_tick10`（TIM6 中断累加） | **10 ms** | 按键扫描、接收超时、闪烁、上报、DHT11 调度 |
| `HAL_GetTick()`（SysTick） | 1 ms | HAL 内部延时 |
| `DWT->CYCCNT` | **1 µs** | DHT11 单总线时序 |

### 一个字节的旅程（★ 最可能被问）

```
PC 按下回车
  ↓  硬件收到 1 个字节，触发 USART1 中断
HAL_UART_RxCpltCallback()          ← main.c，中断上下文
  ↓  调用
Cmd_FeedByte(rx_byte)              ← cmd.c，中断上下文
  ↓  只做：收字节、改接收状态机。绝对不发串口
  ├─ '@'  → 进入 RECVING，记下起始时刻，缓冲存 '@'
  ├─ 'L','E','D','=','1' → 存进缓冲
  └─ '\n' → 置 s_line_ready 标志，回 IDLE
  ↓  中断结束，回到主循环
主循环 10ms 一轮 → Cmd_Tick10ms()
  ↓  发现 s_line_ready
handle_line() → exec_cmd("@LED=1")
  ↓  strcmp 完全匹配
LED_On() + send_str("OK,LED=1\r\n")
```

**为什么不在中断里点灯、发串口？**
- 中断要**快进快出**。串口发送要等硬件，会阻塞几十微秒到几毫秒，拖慢其他中断。
- 中断里做复杂逻辑，一旦出问题极难调试。
- 任务书第 6 条明确要求：**中断只计数/置标志，解析和响应放主循环**。

## 二、五个必答问题（自己先答一遍，别看答案）

<details>
<summary><b>1. 你的 2 秒超时是怎么算出来的？</b></summary>

**当前实现**：TIM6 每 10 ms 中断一次，中断里只 `g_tick10++`。主循环每 10 ms 调一次 `Cmd_Tick10ms()`，收到 `@` 时把 `s_state` 置成 `RECVING`，此后每调一次 `s_timeout++`，到 200 就发 `ERR,TIMEOUT`。200 × 10 ms = 2 s。

**⚠️ 这一版的弱点（老师很可能追问）**：`s_timeout++` 数的是**函数被调用的次数**，不是真实流逝的时间。而 `DHT_Read()` 里有 `HAL_Delay(18)`，主循环每次采样会被阻塞约 20~25 ms，这期间 `g_tick10` 涨了 2~3 个，但 `Cmd_Tick10ms()` 只被调 1 次 → **这些 tick 被丢掉了**，实际超时约 2020 ms？不止，误差约 1%。

**正确写法**（也是你以前用过的老办法）：**别数次数，用 tick 相减**。

```c
/* 收到 '@' 时 */        s_start_tick = g_tick10;
/* 每 10ms 检查  */      if (g_tick10 - s_start_tick >= 200) { ...超时... }
```

无符号相减自动回绕，即使 `g_tick10` 溢出也正确——这句你在 `LED_Key_Control/README.md` 里自己写过。**闪烁（500 ms）和上报（2 s）有同样的问题。**
</details>

<details>
<summary><b>2. 为什么用「逐字节中断」，不用「DMA + 空闲中断」？</b></summary>

协议要求：**从收到 `@` 起 2 秒内没收到 `\n` 就算超时**。

- DMA + 空闲中断（IDLE）：总线安静下来才把**一整块**数据交给回调。你拿到手时已经不知道每个字节**什么时候**到的了，也根本不知道「正在接收中」这个状态。
- 逐字节中断 `HAL_UART_Receive_IT(&huart1, &rx_byte, 1)`：每个字节到达立刻喂给状态机。谁先到、什么时候到，全知道。

**代价**：115200 波特率下每字节约 87 µs 中断一次，CPU 负担比 DMA 高。但本协议最快也就一条 32 字节命令，完全撑得住。
</details>

<details>
<summary><b>3. 定时器中断里做了什么？为什么只做这个？</b></summary>

只做一件事：`g_tick10++`。

- 中断是**抢占式**的，占用时间越长，其他中断被拖延越久（比如串口字节可能丢）。
- 计数是**原子**的（32 位变量读写不会被撕裂），不需要额外保护。
- 真正耗时的活——解析命令、发串口、读 DHT11（要阻塞 18 ms）——全部在主循环，不阻塞任何中断。

⚠️ 顺带：`g_tick10` 被中断和主循环共享，所以必须加 **`volatile`**，否则编译器可能把它优化进寄存器，主循环永远读到旧值。
</details>

<details>
<summary><b>4. <code>LED_GetState()</code> 为什么不存一个变量记住状态？</b></summary>

因为会**两份真相**。

失败场景：假如存了个 `static uint8_t s_state`，`LED_On()` 里写 `s_state = 1`，但 `LED_Toggle()` 里只写了 `ODR ^= LED_PIN`，忘了同步 `s_state`。于是：

```
@BLINK=1  → 灯开始每 500ms 翻转 → 翻了很多次
@LED?     → 返回 s_state（还是启动前的旧值），而灯早就不在那个状态了
```

任务书两句判你不过：
- 必做第 2 条：**「查询应与 LED 实际亮灭一致」**
- 提高任务：**「闪烁中灯状态查询返回当时亮灭」**

**做法**：直接读硬件。共阳极 → `ODR` bit10 = 0 是亮。

```c
return (LED_PORT->ODR & LED_PIN) ? 0 : 1;   /* 1 = 亮，0 = 灭 */
```

**⚠️ 测试陷阱**：测这个 bug 要挑**奇数次翻转**的时刻（比如 2.5 秒 = 5 次）。等 3 秒正好 6 次，**偶数次翻转灯会回到原状态**，bug 会伪装成「通过」。
</details>

<details>
<summary><b>5. 怎么保证非法命令不改变 LED？</b></summary>

因为 `LED_On()` / `LED_Off()` **只在 `strcmp` 完全匹配成功的那一个分支里被调用**。

```c
if (strcmp(cmd, "@LED=1") == 0) {          /* 必须一字不差 */
    s_blink = 0;
    LED_On();
    send_str("OK,LED=1\r\n");
}
```

`@LED=1ABC` → `strcmp` 返回非 0 → 落到最后的 `else` → 只发 `ERR,CMD`，**一次都没碰过 LED**。

`@LED=3`、`@led=1`（小写）同理：协议要求大写，`strcmp` 区分大小写，所以小写也被判非法。
</details>

## 三、其他高频问题快答

| 问题 | 答案要点 |
| --- | --- |
| 超时「只报一次」怎么保证？ | 超时分支里发完 `ERR,TIMEOUT` 立刻 `s_state = ST_IDLE`，下次不再进这个分支；空闲状态根本不判断超时 |
| 超长命令怎么不越界？ | 缓冲 40 字节，最多存 31 个字符（`@` + 30）。存不下时置 `s_overflow` 标志，**余下字符直接丢弃**，等 `\n` 到了报一次 `ERR,LENGTH` |
| 接收中又遇到 `@` 怎么办？ | 丢弃旧命令，重开缓冲、重置计时，以新的 `@` 重新开始 |
| 为什么用 BSRR 不用 `ODR = ...`？ | BSRR 是**原子**操作，一次写就完成置位/复位，不需要「读—改—写」。写成 `ODR ^=` 或 `ODR |= ...` 时，如果中断里改了同一个端口的别的引脚，会被覆盖丢失 |
| BSRR 的 `±16` 怎么记？ | 低 16 位 = 置高（SET）= `1u << n`；高 16 位 = 置低（RESET）= `1u << (n+16)`。权威依据：`Drivers/.../stm32f4xx_hal_gpio.c` 里 `HAL_GPIO_WritePin` 的实现 |
| DHT11 为什么用 DWT 不用 `HAL_Delay`？ | 单总线时序是**微秒**级（50 µs 低电平、26/70 µs 高电平判断 0/1），`HAL_Delay` 最小单位 1 ms，根本不够 |
| 按键怎么消抖？ | 每 10 ms 扫一次，三态机：等按下 → 连续 2 次（20 ms）都读到按下才确认 → 等松开。**在「等松开」状态里不发事件，所以按住不重复触发** |
| 为什么 `.c` 文件第一行要 `#include` 自己的 `.h`？ | 让编译器核对「头文件声明」和「源文件定义」是否一致。比如 `led.h` 写 `void LED_On(void)` 而 `led.c` 写成 `void LED_On(int)`，include 了当场报错；不 include 会拖到链接期才炸（`Undefined symbol` 就是这一类） |
| 串口中断接收，需要**哪两件事**同时成立？ | ① **外设内部**开中断 —— `HAL_UART_Receive_IT()` 干的；② **NVIC 里**使能这个中断源 —— CubeMX 勾 `USART1 global interrupt`（或 `HAL_NVIC_EnableIRQ()`）。**少一个，中断永远不来，而且不报错**，表现为「发什么都不回」。本项目就踩过这个坑：代码调了 `HAL_UART_Receive_IT`，但 `.ioc` 里没勾 USART1 中断 |
| CubeMX 生成的文件（`main.c`、`stm32f4xx_it.c`、`stm32f4xx_hal_msp.c`）能改吗？ | 能，但**只能在 `/* USER CODE BEGIN */ … /* USER CODE END */` 之间改**。块里面 GENERATE CODE 会原样保留，块外面会被冲掉。另外：如果在 CubeMX 里勾了某个中断，CubeMX 会自己生成 `HAL_NVIC_EnableIRQ()` 和对应的 `IRQHandler`，这时自己写在 USER CODE 里的那份就**重复定义**了，必须删掉 |
| 协议要求「忽略 `\r`」，实际调试时会怎么坑你？ | 串口助手的「追加回车」发的是 `\r`（0x0D），「追加换行」发的才是 `\n`（0x0A）。板子只认 `\n`，而 `\r` 被故意忽略了 —— 所以勾错选项的表现**和"没收到结束符"一模一样**：等 2 秒后报 `ERR,TIMEOUT`。用 HEX 发送 `40 4C 45 44 3D 31 0A` 可以绕过助手设置，100% 确定线上发的是什么 |

## 四、老师「指定的小修改」会考什么

验收会当场让你改一个小地方。**全是改常量或改一个分支**，考的是「你知不知道那个数字在哪、单位是什么」。

**你现在就该能答出每个数字的位置：**

| 要改成 | 改哪个文件 | 哪个常量 / 表达式 | 单位 |
| --- | --- | --- | --- |
| 超时 2 秒 → 1 秒 | `cmd.c` | `TIMEOUT_TICKS` | 个 10 ms |
| 闪烁 500 ms → 200 ms | `cmd.c` | `BLINK_TICKS` | 个 10 ms |
| 上报周期 2 秒 → 5 秒 | `cmd.c` | `REPORT_TICKS` | 个 10 ms |
| DHT11 采样 2 秒 → 1 秒 | `main.c` | `if (g_tick10 - t_dht >= 200)` | 个 10 ms |
| 时基 10 ms → 5 ms | `main.c` | `MX_TIM6_Init()` 的 `Period` | `(PSC+1)×(ARR+1)÷90MHz` |
| 按键消抖 20 ms → 50 ms | `key.c` | `DEBOUNCE_TICKS` | 个 10 ms |
| LED 换成 PH11 | `led.c` | `LED_PIN` 宏 | — |
| 加一条 `@LED!` 翻转命令 | `cmd.c` | 加一个 `else if` 分支调 `LED_Toggle()` | — |
| 按键改成「按一下翻转」 | `main.c` | 按键分支改成 `LED_Toggle()` | — |

### 建议的练习（休息好之后做，30 分钟）

1. **把超时改成 1 秒**，编译、串口验证。（顺手把「数次数」改成「tick 相减」会更好）
2. **加一条 `@LED!` 命令**，让灯翻转，响应 `OK,LED=1` 或 `OK,LED=0`（返回翻转后的状态）。
3. **改时基**：把 TIM6 的 `Period` 从 99 改成 49（→ 5 ms）。⚠️ 注意：这样所有「个数」都要翻倍——`TIMEOUT_TICKS` 200 → 400，以此类推。**这个坑老师很可能拿来考你。**

改完一个就编译下载验证一次。**这三件事做完，现场验收基本就稳了。**

## 五、诚实面对的两块软肋

如果老师问到，**别硬撑，说清楚**——他知道你懂原理，反而加分。

| 软肋 | 怎么说 |
| --- | --- |
| 超时用「调用次数」而不是 tick 差值 | 「这一版是按 `Cmd_Tick10ms` 被调用的次数算的，误差约 1%，因为 DHT11 读取会阻塞 20 ms 吃掉几个 tick。正确做法是记录起始 tick，用 `g_tick10 - start >= 200` 判断，无符号相减自动回绕。」 |
| 中断和主循环共用接收缓冲 | 「正常情况下没有冲突，因为主循环 10 ms 就处理一次。但如果 10 ms 内连发两条命令，或者主循环正好卡在 DHT11 读取里，可能丢掉一条响应。彻底解决要让中断只往环形缓冲塞字节，状态机整体搬到主循环。」 |

**把弱点讲清楚，比背一段完美说辞更能证明你懂。**
